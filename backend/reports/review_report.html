Possible Bugs 3 item(s)

  • `clients.responses.parse(...)` assumes the OpenAI SDK version exposes `responses.parse` and `output_parsed`; older/newer SDKs may raise at runtime and always fall back to demo mode.
  • The OpenAI request passes the diff inline without chunking beyond 20k chars; larger changes may be truncated and reduce review quality.
  • `load_dotenv()` is called inside `review_diff()` on every invocation, which may unexpectedly override environment handling in some runtime contexts.

Missing Tests 3 item(s)

  • No tests cover the new OpenAI review path, including fallback behavior when the API key is missing or the response schema validation fails.
  • No tests verify that `_truncate_diff()` preserves valid JSON-safe input and truncates long diffs as expected.
  • No tests cover the new UTF-8 `errors='replace'` subprocess settings for non-ASCII repository paths/output.

Suggested Test Cases

  • Set `AI_REVIEW_MODE=openai` with a valid stubbed OpenAI client and assert a `ReviewResult` is returned from parsed structured output.
  • Set `AI_REVIEW_MODE=openai` without `OPENAI_API_KEY` and assert the function falls back to demo mode with a warning appended to `project_summary`.
  • Simulate an OpenAI API exception and confirm demo fallback occurs instead of crashing.
  • Provide a diff longer than 20,000 characters and verify `_truncate_diff()` appends the truncation notice.
  • Run git/test subprocesses against paths or output containing non-UTF-8 bytes and verify the reader/test runner still return results instead of failing.

Security & Reliability Concerns

  • Sending full diffs to a third-party API may expose sensitive code or secrets if users enable OpenAI mode without reviewing repository contents.
  • `except Exception` in the OpenAI path swallows all errors and can hide integration problems behind demo-mode fallback, making failures less visible.
  • Adding `openai` without a pinned version may introduce breakage from SDK API changes.
